# SillyTavern 聊天文件管理扩展设计

## 1. 项目范围

- 目标版本：SillyTavern 1.18.0
- 扩展名称：SillyTavern Chat Manager（聊天管理）
- 扩展形态：纯前端第三方扩展
- 设计原则：不修改 SillyTavern 源码，不依赖服务端插件，不接管原生保存流程

扩展只提供三项用户功能：

1. 随时查看并打开全部有效聊天
2. 识别指定聊天对应的原生备份
3. 按消息楼层分割指定聊天

缓存、分页、流式读取和 DOM 防重复注入仅是内部实现手段，不作为用户功能，也不声称优化 SillyTavern 核心。

## 2. 明确不做

- 不修改服务端中文备份名变成下划线的规则
- 不修改聊天保存时完整重写 JSONL 的逻辑
- 不自动删除、截断、替换或分割聊天
- 不改变模型上下文、提示词或生成流程
- 不提供大文件警告、风险等级或后台监控
- 不提供高级排序、内容深度搜索或批量操作
- 不持久化分割表单参数，不提供缓存管理或本地分卷导出
- 不处理无法归属到现有角色或群组的根级孤立聊天
- 不恢复已被覆盖、轮换删除或物理丢失的备份

## 3. 界面结构

### 3.1 统一入口

原生“聊天文件”菜单项为 `#option_select_chat`。扩展在其后插入唯一入口：

```html
<a id="chat_manager_open">
    <i class="fa-lg fa-solid fa-folder-tree"></i>
    <span>聊天管理</span>
</a>
```

插入方式：

```js
document
    .querySelector('#option_select_chat')
    ?.insertAdjacentElement('afterend', entry);
```

点击“聊天管理”打开扩展自己的全局聊天面板。桌面端和移动端使用同一个入口，不创建顶栏按钮、浮动按钮或设置页备用入口。该入口不依赖当前角色或群聊：即使 `characterId` 和 `groupId` 都为空，仍可打开面板并从全部聊天中选择一条记录。

入口在 `APP_READY` 后执行幂等初始化：先按固定 ID 查重，再插入并绑定扩展自己的点击处理。找不到 `#option_select_chat` 时只禁用该入口并报告版本兼容错误，不修改相邻原生菜单结构。

### 3.2 原生聊天文件列表增强

原生聊天文件列表保留原有数据、布局和操作。扩展仅在每条记录的操作区末尾增加两个按钮：

```text
导出 JSONL　导出 TXT　删除　备份　分割
```

使用的原生选择器：

| 用途 | 选择器 |
| --- | --- |
| 聊天列表 | `#select_chat_div` |
| 聊天行 | `.select_chat_block_wrapper` |
| 精确文件名 | `.select_chat_block[file_name]` |
| 行操作区 | `.select_chat_actions` |

每个增强过的聊天行添加 `data-chat-manager-enhanced="true"`，避免面板重新渲染后重复插入按钮。按钮使用事件委托，不覆盖原生事件；点击时阻止冒泡，不能同时触发打开、导出或删除聊天。

### 3.3 最终交互

```text
聊天选项菜单
├─ 聊天文件
└─ 聊天管理

原生聊天文件列表
└─ 当前角色或群组的聊天：备份｜分割

聊天管理面板
└─ 全部有效聊天：打开｜备份｜分割
```

“当前聊天”与“面板中选中的记录”是两个独立概念。备份识别和分割始终使用记录自身携带的所有者类型、所有者 ID 与聊天文件 ID，不依赖页面当时打开的角色或群聊。点击“打开”才切换酒馆当前上下文。

### 3.4 运行状态与操作权限

| 状态 | 打开、筛选和刷新管理面板 | 查看、下载或恢复备份 | 打开所选聊天 | 自动更新分割预览 | 确认分割 |
| --- | --- | --- | --- | --- | --- |
| 已选择角色或群聊，未生成 | 允许 | 允许 | 允许 | 允许 | 允许 |
| 未选择角色或群聊，未生成 | 允许 | 允许 | 允许；所选记录决定目标 | 允许；所选记录决定目标 | 允许；所选记录决定目标 |
| 正在生成或流式输出 | 允许，只读操作不切换上下文 | 允许 | 禁止 | 禁止 | 禁止 |
| 插件正在写入或校验分卷 | 允许查看现有面板 | 允许 | 禁止 | 禁止重复启动 | 禁止重复启动 |

扩展初始化时调用原生 `isGenerating()` 取得当前状态，避免扩展恰好在生成中加载却漏掉开始事件；随后监听 `GENERATION_STARTED`、`GENERATION_ENDED` 和 `GENERATION_STOPPED`。开始生成时立即禁用会切换聊天或写入文件的操作，结束或停止后重新计算按钮状态。不得只判断 `streamingProcessor`，因为非流式生成和群聊生成同样需要拦截。

角色索引 `0` 是有效值，判断“未选择角色”必须使用 `characterId === undefined || characterId === null`，不能使用简单的真假判断。

### 5.1 请求与返回字段

- `/api/chats/recent`：请求体传 `metadata: true` 并省略 `max`；记录使用原生字段 `file_id`、`file_name`、`file_size`、`chat_items`、`mes`、`last_mes`、`chat_metadata`，所有者字段是单聊的 `avatar` 或群聊的 `group`
- `/api/characters/chats`：请求体至少包含 `avatar_url`；只查名称冲突时传 `simple: true`，读取来源指纹时传 `metadata: true`
- `/api/chats/get`：请求体包含 `avatar_url` 和不带 `.jsonl` 的 `file_name`
- `/api/chats/group/get`：请求体包含不带 `.jsonl` 的 `id`
- `/api/chats/group/info`：请求体包含不带 `.jsonl` 的 `id`；用于群聊来源指纹
- `/api/chats/export`：群聊名称占用探测传 `is_group: true`、带 `.jsonl` 的 `file`、`exportfilename` 和 `format: "jsonl"`；404 才表示目标文件不存在。若返回 200，只需确认占用并立即取消响应体，不解析文件内容
- `/api/backups/chat/download`：请求体必须是列表接口返回的服务器实际名称 `{ "name": file_name }`
- `/api/chats/save`：请求体包含 `avatar_url`、不带扩展名的 `file_name`、完整 `chat` 数组和 `force: false`
- `/api/chats/group/save`：请求体包含不带扩展名的 `id`、完整 `chat` 数组和 `force: false`
- `/api/groups/edit`：服务端会用请求体整体覆盖群组 JSON，因此不得只发送 `id` 和 `chats`

保存分卷前必须使用原生 `compressRequest()` 包装请求，和酒馆自身的大聊天保存方式一致。不得设置 `force: true` 绕过完整性检查。

### 5.2 原生聊天文件边界

1. 聊天文件是 JSONL；第一行是聊天头，后续每一行对应一个消息对象。当前聊天头应包含对象型 `chat_metadata`；兼容旧文件时也接受明确包含 `user_name` 或 `character_name` 的旧聊天头，并把缺失的元数据初始化为空对象
2. `/api/chats/get` 和 `/api/chats/group/get` 成功但文件不存在时可能返回空对象或空数组，不保证使用 404；插件必须检查响应类型
3. 服务端读取普通聊天时会跳过无法解析的 JSONL 行。插件必须把返回数组长度与列表接口的 `chat_items + 1` 比较；不一致时视为来源损坏并禁止分割
4. 只有聊天头、没有消息的空聊天可以浏览和打开，但 `N = 0` 时没有合法楼层，禁用分割
5. 文件 ID 在内部统一不带 `.jsonl`；调用列表或下载接口时保留原生 `file_name`，不得混用
6. 所有者的稳定身份是单聊头像文件名 `avatar` 或群组 `group` ID，角色名、群组名和消息显示名只用于展示
7. 输出名先连同 `.jsonl` 调用 `/api/files/sanitize-filename`，预览和冲突检测都使用清理后的实际 `file_id`。清理结果为空、扩展名被截断或无法保留数字后缀时禁止写入
8. 原生文件名清理存在字节长度上限。构造分卷名时必须先为 `.jsonl`、楼层范围和冲突数字后缀预留空间，再截短原聊天名；不能先拼接超长名称后依赖服务端静默截断

### 5.3 纯前端性能边界

备份下载接口返回原始 JSONL 响应体，可以在浏览器中使用 `ReadableStream` 逐行解析。普通聊天的原生读取接口则返回完整 JSON 数组，原生 JSONL 导出接口也会把全文包装进 JSON，均不能真正流式取得源文件。

因此纯前端版本可以避免一次渲染全部消息、避免额外拼接完整文本并按卷串行释放临时数据，但首次读取待分割的普通聊天仍需要完整进入浏览器和服务端内存。插件不得宣传为消除超大文件读取开销；若未来需要真正的源聊天流式切分，才需要新增服务端能力。

## 6. 功能一：全部聊天

### 6.1 获取数据

调用 `POST /api/chats/recent` 时传 `metadata: true` 并省略 `max`，一次取得当前账号全部有效单聊和群聊及其聊天头元数据。该接口也会枚举根级聊天，但扩展只保留能映射到现有角色或群组的记录。接口返回：

- 实际聊天文件名
- 角色头像文件名或群组 ID
- 文件大小
- 消息数量
- 最后一条消息
- 最后消息时间
- 插件分卷元数据（存在时）

前端通过 `characters` 和 `groups` 补充角色或群组显示名。

无法匹配现有角色或群组的记录不展示，因为原生前端无法可靠打开它们。记录的内部主键使用 `ownerType + ownerId + file_id`，不能只用聊天文件名；不同角色可以存在同名聊天。

### 6.2 面板内容

每条记录只显示：

- 角色或群组名称
- 聊天文件名
- 最后消息时间
- 文件大小
- 消息数量

记录操作只保留：

- 进入聊天
- 查找备份
- 创建分卷

面板提供一个输入框，只过滤角色名、群组名和聊天文件名。列表固定按最后消息时间倒序，不提供其他排序方式。

单击聊天行或“进入聊天”会切换到目标聊天。“查找备份”和“创建分卷”只使用该记录的稳定主键，不依赖当前打开的角色或群聊。

### 6.3 分组显示

工具栏提供两个彼此独立的切换按钮：

- “合并角色”：按 `ownerType + ownerId` 把同一角色或群组的聊天折叠为一组
- “合并分卷”：按同一所有者和分卷元数据中的 `rootChatId` 折叠分卷

两个开关可以同时启用，此时先按角色或群组分组，再在组内合并分卷。分卷组不依赖原始聊天存在；若同一所有者下存在文件 ID 与根聊天 ID 完全相同的聊天，则放入同组并标记为“源”。折叠状态仅保留在当前页面内，两个分组开关保存为扩展显示偏好。

分卷关系和增量配置都只读取聊天头中的 `chat_metadata.chat_manager`。文件名即使符合分卷外观但没有有效元数据，也按普通聊天显示，不参与分组或参数推断。

### 6.4 打开聊天

单聊：

1. 用 `avatar` 找到角色 ID
2. 调用 `selectCharacterById()`
3. 按原生欢迎页流程调用 `setActiveCharacter()` 并保存活动实体设置
4. 从 `file_name` 去掉 `.jsonl`
5. 若目标尚未打开，调用 `openCharacterChat(chatName)`

群聊：

1. 调用 `openGroupById(groupId)`
2. 按原生欢迎页流程调用 `setActiveGroup()` 并保存活动实体设置
3. 从 `file_name` 去掉 `.jsonl`
4. 确认目标 ID 仍存在于该群组 `chats` 后，调用 `openGroupChat(groupId, chatName)`

打开前再次调用 `isGenerating()`，而不是只信任按钮渲染时的状态。正在生成或流式输出时禁止切换聊天；目标角色、群组或聊天已经被删除时保持当前上下文不变。

### 6.5 刷新与显示

- 第一次打开面板时请求全部聊天
- 同一次页面会话再次打开时复用内存数据
- 用户点击“刷新”时重新请求全部聊天
- 列表固定每页 50 条

不提供刷新数量、分页数量或缓存清理设置。

## 7. 功能二：对应备份

### 7.1 问题来源

原生备份使用：

```js
sanitize(name).replace(/[^a-z0-9]/gi, '_').toLowerCase()
```

中文角色卡可能得到相同的下划线前缀，因此不能只凭备份文件名判断归属。

### 7.2 读取方式

1. 调用 `/api/backups/chat/get` 获取服务器实际文件名
2. 将实际文件名原样传给 `/api/backups/chat/download`
3. 解析 JSONL 聊天头和消息

下划线不影响读取；它只导致文件名无法直接辨认。

### 7.3 匹配顺序

针对用户点击“备份”的精确聊天执行匹配：

1. 用角色头像文件名或群聊聊天 ID 生成备份前缀候选
2. 比较备份和目标聊天的 `chat_metadata.integrity`
3. 对规范化消息序列计算 SHA-256
4. 验证备份是目标聊天的完整快照或历史前缀

完成检查后显示三种结果状态：

- 已匹配：身份与消息序列均能验证
- 需要确认：证据相关但无法唯一验证
- 无法识别：没有足够证据

“需要确认”只在当前操作中由用户选择，不保存长期手动绑定。

### 7.4 展示与操作

从聊天行点击“备份”后，只展示与该聊天相关的备份候选，包括：

- 原始下划线文件名
- 备份时间
- 文件大小
- 消息数量
- 最后一条消息的时间与摘要
- 匹配状态
- 匹配依据

备份列表接口返回后，立即创建全部文件名候选卡片并显示“等待检查”，不等待原聊天或候选备份内容下载。随后使用有限并发读取文件；每个候选完成时原位更新为匹配结果，确定无关的候选从列表移除。顶部持续展示候选总数、已检查数量和已确认数量，并显示实际进度条。

操作包括“恢复为新聊天”“查看内容”和“下载文件”。恢复复用酒馆公开的 `importCharacterChat` 或 `importGroupChat` 导入链路，创建一份新的聊天记录并保留原聊天；插件不直接覆盖现有聊天。删除和批量管理继续使用酒馆原生功能。

“查看内容”使用分页或虚拟列表，只渲染当前可见消息；禁止像原生查看器一样先把全部消息拼成一个巨型文本框。解析备份时只保留匹配所需摘要和当前查看窗口，关闭面板后释放流读取结果。

聊天文件管理主面板及所有二级弹窗，包括对应备份、备份内容、分割操作和任务恢复，只能通过明确的关闭按钮或操作完成链路关闭。点击遮罩区域不得关闭，避免长时间读取或已填写参数因误点击丢失。

### 7.5 限制

- 原聊天已删除且备份缺少 `integrity` 时可能无法唯一识别
- 分支或检查点可能共享 `integrity`，必须继续比较消息序列
- 被同名覆盖的旧内容无法恢复
- 被原生轮换删除的备份无法恢复
- 插件不修改今后生成的备份文件名

## 8. 功能三：按消息楼层分割

### 8.1 支持来源

分割只作用于全局聊天面板或原生聊天文件列表中选中的有效单聊、群聊。备份文件不参与分割。

原聊天在整个流程中只读并始终保留。插件只根据原记录快照创建新的酒馆聊天文件，不重命名、不截断、不删除原聊天，也不提供本地分卷导出。

来源由选中记录的 `ownerType + ownerId + file_id` 确定。即使页面没有当前角色或群聊，也可以直接读取并分割该记录；插件不得为了分割而先打开聊天或切换页面上下文。

### 8.2 来源稳定读取

自动生成首个预览前执行以下顺序：

1. 从 `/api/characters/chats` 或 `/api/chats/group/info` 取得来源指纹 A
2. 调用对应聊天读取接口取得 `[chatHeader, ...messages]`
3. 再次取得来源指纹 B
4. 要求 A 与 B 的 `ownerId`、`file_id`、`file_size`、`chat_items` 和 `last_mes` 一致；单聊元数据接口能够返回时再比较 `chat_metadata.integrity`
5. 按原生当前格式或明确的旧格式验证第一项是聊天头，返回消息数等于 `chat_items`，所有楼层都能解析为对象；旧聊天缺少 `integrity` 时允许读取，但使用其他指纹完成稳定性检查

任一步不满足都不生成预览。指纹检查用于发现读取期间发生的原生保存；它不声称替代文件锁。原聊天始终保留，因此极端情况下未被指纹发现的同大小编辑只会让分卷成为稍早的只读快照，不会覆盖较新的原聊天。

### 8.3 楼层定义

使用 SillyTavern 原生 `mesid`：

- 第一条消息是 `#0`，对应 `chat[0]`
- 最后一条消息是 `#(N - 1)`
- JSONL 第一行聊天头不算楼层
- 系统消息和隐藏消息只要存在于聊天数组中就占用原生楼层
- 一个楼层的全部 Swipe 和附加字段整体保留

界面始终显示 `#mesid`，不引入从 1 开始的另一套编号。

### 8.4 模式 A：指定范围

用户填写起始楼层 `#S` 和结束楼层 `#E`，两端都包含：

```text
0 <= S <= E < N
```

输出一个包含 `#S..#E` 的新聊天。范围外消息不复制，仍完整保存在原聊天中。

### 8.5 模式 B：固定楼层数

用户填写每卷楼层数 `X`，输入框默认值为 500。

默认对完整聊天 `#0..#(N-1)` 分卷，也可以先填写 `#S..#E`，只处理指定范围。

示例：范围 `#100..#349`，每卷 100 层：

```text
#100..#199
#200..#299
#300..#349
```

最后不足 `X` 层的余数单独成为最后一卷。

### 8.6 分割操作面板与预览

点击“分割”只打开操作面板，不产生任何文件写入。操作面板按以下顺序工作：

1. 显示只读来源信息：角色或群组、聊天文件名、总楼层数
2. 选择“指定范围”或“固定楼层数”
3. 填写 `#S`、`#E`；固定量模式再填写 `X`
4. 输入变化停止 300ms 后自动计算分卷计划，此时仍不写入文件
5. 检查自动更新的预览列表
6. 点击“确认创建分卷”后才开始创建新聊天

预览列表显示：

```text
原聊天名 [分卷 001-of-003] [#100-#199]　100 层　预计大小
原聊天名 [分卷 002-of-003] [#200-#299]　100 层　预计大小
原聊天名 [分卷 003-of-003] [#300-#349]　 50 层　预计大小
```

面板主操作：

```text
确认创建分卷　完成当前卷后停止
```

- 关闭面板会取消尚未完成的预览计算并丢弃计划，零写入
- 修改任何输入后，旧预览立即失效；防抖结束后自动生成新预览
- 连续修改会取消上一轮预览，旧异步结果不得覆盖最新参数的预览
- 首次稳定读取后可以复用来源快照计算后续预览，写入前仍必须重新校验来源指纹
- 未生成有效预览时，“确认分割”不可用
- 确认前重新取得来源指纹 C；与 B 不一致时中止并自动生成新的稳定预览
- 确认按钮处理时再次调用 `isGenerating()`；生成已经开始时保持预览但拒绝写入
- 只有“确认分割”可以调用写入接口

### 8.7 内容规则

- 只在消息对象之间切分
- 不拆开消息、Swipe、附件引用、推理字段或其他扩展字段
- 不插入总结
- 不复制范围外上下文
- 不修改原消息对象
- 不覆盖已有聊天文件

### 8.8 分卷元数据

每个分卷从原 `chat_metadata` 深拷贝需要随聊天保留的设置，例如角色设定覆盖、Persona、聊天变量和附件清单；随后执行以下处理：

- 删除原 `integrity` 并生成独立 UUID
- 删除 `main_chat`，避免新分卷被误认为原有分支或检查点
- 删除 `chat_id_hash` 和 `lastInContextMessageId` 等依赖原文件名或原楼层编号的派生缓存，交由酒馆重新计算
- 覆盖已有 `chat_manager`，把当前来源记录为直接父级；若来源本身是分卷，可额外保留其根来源 ID 作为追踪信息

不得修改消息对象中的任何字段。最终聊天头记录最小来源信息：

```json
{
  "chat_metadata": {
    "integrity": "独立 UUID",
    "chat_manager": {
      "schema": 1,
      "sourceChatId": "原聊天 ID",
      "rootChatId": "分卷组根 ID",
      "sourceIntegrity": "原 integrity",
      "sourceStart": 100,
      "sourceEnd": 199,
      "messageDigest": "本卷消息 SHA-256",
      "splitMode": "fixed",
      "chunkSize": 100,
      "sequence": 2,
      "incremental": false,
      "createdAt": "ISO-8601"
    }
  },
  "user_name": "unused",
  "character_name": "unused"
}
```

`chat_manager` 只存在于新分卷的聊天头，不写入消息对象，不修改原始聊天，也不会作为消息正文发送给模型。它增加的体积固定且很小。插件用这段元数据精确读取增量分卷配置；不另外保存一份分割配置，也不根据文件名区间长度推断参数。

### 8.9 输出命名

```text
<原聊天名> [分卷 001-of-003] [#100-#199]
<原聊天名> [分卷 002-of-003] [#200-#299]
<原聊天名> [分卷 003-of-003] [#300-#349]
```

指定范围只生成一个新聊天时使用 `<原聊天名> [#S-#E]`，不添加分卷序号。

写入前查询同一所有者的已有聊天名，并对每个候选名执行原生文件名清理。若清理后的目标名称已存在，则在完整目标名后追加短数字后缀，从 `-2` 开始递增尝试，直到找到可用名称。例如 `原聊天名 [#100-#199]` 已存在时，依次使用 `原聊天名 [#100-#199]-2`、`原聊天名 [#100-#199]-3`。预览必须展示清理后将实际写入的名称。插件绝不主动选择或强制覆盖已知的现有文件。

原生保存接口不是“仅当文件不存在时创建”的原子接口。插件在同一页面内用写入互斥锁串行执行，并在每卷写入前重新检查名称；若浏览器支持 Web Locks，再按账号内所有者加锁以协调同源标签页。其他设备恰好同时创建同名的极端竞态无法由纯前端彻底消除；服务端文件已有不同 `integrity` 时原生检查会拒绝覆盖，但旧文件缺少 `integrity` 时没有同等保证。需要绝对的跨客户端排他创建时必须增加服务端 create-only 能力。

### 8.10 写入、登记与验证

所有分卷串行处理，一卷完成写入、回读和登记后才开始下一卷。每次保存都使用 `compressRequest()`，不并发提交多个大请求。

单聊每卷流程：

1. 再次确认目标名在该角色下不存在
2. 调用 `/api/chats/save`
3. 调用 `/api/chats/get` 回读验证
4. 通过请求体带 `simple: true` 的 `/api/characters/chats` 确认实际文件 ID 可枚举

群聊每卷流程：

1. 再次确认目标名既不在最新群组 `chats` 中，也不存在于本批次已创建名称中；同时用 `/api/chats/export` 精确探测文件，排除已存在但尚未登记的同名群聊文件
2. 调用 `/api/chats/group/save`
3. 调用 `/api/chats/group/get` 回读验证
4. 调用 `/api/groups/all` 取得最新群组对象；仅在 `chats` 不含目标 ID 时追加一次
5. 将完整最新群组对象提交给 `/api/groups/edit`
6. 再次读取群组数据，确认目标 ID 已登记后才算该卷成功

每个分卷写入后立即回读并验证：

1. 文件存在
2. 楼层范围和消息数量正确
3. 规范化消息摘要与预览计划一致
4. 固定量模式的所有分卷按顺序拼接后，与所选来源范围一致

摘要按消息逐条规范化并计算，再用固定顺序聚合，避免先构造包含整卷消息的第二份巨型字符串。预计大小按最终聊天头、每条 JSONL 序列化后的 UTF-8 字节数和换行符计算。

任何分卷失败时停止后续写入。原聊天不受影响；界面区分“已验证并登记”“文件已创建但群聊登记失败”“写入或校验失败”，列出实际创建的名称并提供重试登记，不自动删除。

### 8.11 增量分卷

分卷组以同一所有者和 `rootChatId` 为身份，不要求原始聊天仍然存在。最后一卷继续产生消息后，组卡片提供“增量分卷”：

1. 从最后一卷聊天头读取其原始逻辑范围和精确分割配置
2. 只把该卷原始范围之后新增的本地消息纳入预览
3. 新卷序号从组内最大序号继续，逻辑楼层从已有最大结束楼层之后继续
4. 固定楼层模式默认沿用最后一卷保存的 `chunkSize`
5. 组内其他分卷明确保存过的固定楼层配置列为可选项；用户也可以在本次操作中改成自定义配置
6. 新配置随新分卷写入聊天头，下次直接读取，不写入扩展设置，也不从共同范围特征推断

增量操作仍遵守只创建新记录、不截断来源卷的规则。最后一卷没有新增消息、元数据缺失或逻辑范围不连续时禁用该操作并显示原因。

### 8.12 原生备份副作用

`/api/chats/save` 和 `/api/chats/group/save` 在服务端都会调用酒馆原生聊天备份逻辑。确认分割可能生成新的备份，并受酒馆现有的节流、单聊天保留数和总备份数配置影响；达到上限时，酒馆可能轮换删除最旧备份。

纯前端扩展无法在保持原生保存接口的同时关闭这项副作用。确认面板必须在写入前明确显示“创建分卷会触发酒馆原生备份与轮换规则”，但插件不自行删除、重命名或修改任何备份。

## 9. 内部实现约束

这些约束不作为用户功能：

- 备份 JSONL 使用流式逐行解析，避免额外复制整个大文件
- 全部聊天列表使用固定 50 条分页
- 同一次页面会话复用已取得的聊天列表
- 原生聊天行注入必须幂等
- 网络请求支持 `AbortController`
- 普通聊天读取接受原生接口必须完整返回数组的限制，不再制造第二份完整消息文本
- 分卷写入使用单任务互斥锁，重复点击确认不得启动第二个任务
- 写入开始前允许取消；写入开始后“停止”只阻止下一卷，不中断正在提交或登记的当前卷
- 若分卷任务进行中收到 `GENERATION_STARTED`，不阻止酒馆生成；当前提交或登记步骤完成后停止后续分卷，并要求用户在生成结束后继续
- 确认写入前把所有者、来源指纹、目标名、范围、预期摘要和逐卷状态写入 IndexedDB 任务日志；每个写入、回读和群聊登记阶段完成后立即更新
- 扩展启动时只读检查未完成任务日志，按目标名回读并展示恢复报告；恢复过程不自动补写或删除文件，用户确认后才可继续未开始的卷或重试登记
- 所有来自聊天名、角色名、消息和备份名的界面内容使用 `textContent`，不得拼接进 `innerHTML`
- 消息摘要逐条计算并按顺序聚合，临时数组和编码缓冲在每卷验证后释放
- 业务算法与 DOM 操作分离

扩展不提供与这些实现细节相关的用户设置。

## 10. 错误处理

| 场景 | 行为 |
| --- | --- |
| 全部聊天接口失败 | 显示错误并保留当前面板状态 |
| 目标角色或群组不存在 | 禁止打开、备份匹配和分割 |
| 备份下载返回 404 | 显示备份已不存在 |
| 备份 JSONL 损坏 | 报告损坏，不继续匹配 |
| 备份证据不唯一 | 显示“需要确认”，不自动归属 |
| 未选择角色或群聊 | 正常展示全部聊天；操作使用选中记录的所有者，不自动创建临时角色 |
| 正在生成或流式输出 | 保留只读浏览和备份查看，禁用打开聊天、预览分割和确认写入 |
| 空聊天 | 允许浏览和打开，禁用分割 |
| 来源返回空对象、聊天头无效或消息数不符 | 标记来源不存在或损坏，禁止分割 |
| 楼层输入越界 | 阻止进入预览 |
| 每卷楼层数小于 1 | 阻止进入预览 |
| 原聊天在预览后发生变化 | 使预览失效并重新读取来源生成预览 |
| 文件名清理后为空、截断异常或发生冲突 | 重新生成带数字后缀的安全名称；无法生成时禁止写入 |
| 请求体过大或返回 413 | 停止任务，建议缩小每卷楼层数；不自动改变用户范围 |
| 保存请求断线、结果未知 | 先按预定名称回读；内容摘要一致则视为已写入，否则停止，禁止盲目重试 |
| 写入失败 | 停止后续分卷，保留原聊天 |
| 回读摘要不符 | 标记失败，停止后续分卷 |
| 群聊文件已验证但登记失败 | 标记“文件已创建、未登记”，停止后续分卷并提供登记重试 |
| 页面刷新或关闭 | 不能保证继续任务；重新打开后按预定名称回读并报告已完成卷，不自动重写 |
| 原生 DOM 选择器变化 | 禁用对应入口或行按钮并报告兼容错误 |

## 11. 验收标准

### 11.1 全部聊天

1. 不返回欢迎页也能打开“聊天管理”
2. 能列出全部有效单聊和群聊
3. 能按角色、群组或聊天文件名过滤
4. 默认按最后消息时间倒序
5. 能精确打开选中的单聊或群聊
6. 每页最多渲染 50 条记录
7. 未选择角色或群聊时仍能打开面板、选中记录并进入对应操作
8. 单击选中记录不会切换酒馆上下文，只有“打开”会切换
9. 生成开始后不能通过面板切换聊天，生成结束或停止后操作状态恢复
10. 可以分别按角色或群组、按分卷组折叠和展开列表
11. 原始聊天存在时位于对应分卷组内并标记为“源”，不存在时分卷组仍然成立

### 11.2 对应备份

1. 下划线前缀相同的两张中文卡不会仅凭文件名自动归属
2. `integrity` 和消息序列匹配时显示“已匹配”
3. 分支共享 `integrity` 时继续使用消息摘要消歧
4. 证据不足时显示“需要确认”或“无法识别”
5. 可以将备份恢复为新聊天、分页查看或下载原始文件
6. 不重命名、删除或修改原生备份
7. 查看大型备份时不会一次性创建包含全部消息的 DOM 或巨型文本框
8. 备份列表返回后立即显示候选卡片，各文件完成读取时原位更新，不等待全部扫描完成
9. 点击主面板或任意二级弹窗外的遮罩区域不会关闭界面

### 11.3 聊天分割

1. 指定范围包含 `#S` 和 `#E`
2. 指定范围不会复制范围外消息
3. 固定量模式每卷最多 `X` 层
4. 固定量模式完整保留最后余数卷
5. 限定范围后固定量分割不会越过 `#S` 或 `#E`
6. Swipe、附件引用、推理字段和其他消息字段完整保留
7. 原聊天在成功、失败和取消时均保持不变
8. 不覆盖已有聊天文件
9. 每个新分卷拥有独立 `integrity`
10. 写入后回读的数量和摘要验证通过
11. 打开操作面板和自动更新预览均不会写入文件
12. 取消操作不会产生任何分卷
13. 原聊天在预览后变化时不能使用旧计划写入
14. 空聊天、无效聊天头、损坏行和消息数不符时均禁止分割
15. 文件名经过原生清理和长度处理后仍保留扩展名、范围及必要的数字冲突后缀
16. 单聊和群聊的大请求均经过原生请求压缩
17. 群聊只有在文件回读通过且 `group.chats` 登记成功后才标记完成
18. 保存结果未知时先回读判定，不会盲目重复创建
19. 创建分卷前明确显示会触发酒馆原生备份与轮换规则
20. 正在生成时不能确认写入；生成开始前已有的预览也不能直接提交
21. 没有当前角色或群聊时，可以直接对管理面板选中的有效记录生成预览和分割
22. 分割过程中开始生成时，不干预原生生成；当前卷完成安全落点后停止后续卷
23. 页面刷新后能从任务日志回读并区分已完成、结果未知和未开始的卷，且不会自动补写
24. 最后一卷有新增消息时可以继续增量分卷，序号和逻辑楼层连续
25. 增量分卷只读取聊天头中明确保存的配置，不从文件名范围推断配置
26. 修改配置后，新分卷保存新配置，并可在后续增量操作中作为组内选项

### 11.4 原生聊天文件列表

1. 每条聊天记录最多出现一个“备份”和一个“分割”按钮
2. 原生列表重新渲染后不会重复注入
3. 行按钮能取得当前所有者和精确聊天文件名
4. 点击扩展按钮不会同时触发其他原生操作
5. 行增强失效不影响原生聊天文件功能

## 12. 实施顺序

### 阶段一：扩展骨架与全部聊天

- `manifest.json`、入口和全局面板
- 全部聊天列表、简单过滤、固定分页
- 无当前角色时的记录选择，以及生成状态操作门禁
- 精确打开单聊和群聊
- 原生聊天行按钮注入

### 阶段二：对应备份

- 备份列表和按需下载
- 前缀、`integrity` 和消息指纹匹配
- 流式匹配、分页查看与原始下载

### 阶段三：聊天分割

- 指定范围和固定楼层数
- 来源稳定读取、原生文件边界校验和安全命名
- 只读操作面板、分割预览、原生备份副作用提示和确认门槛
- 单聊和群聊串行压缩写入、群聊登记
- 任务日志、回读验证和部分失败恢复报告

## 13. 最终功能结构

```text
聊天管理
├─ 全部聊天：进入聊天｜查找备份｜创建分卷
│  └─ 显示：合并角色｜合并分卷｜展开或收起
├─ 备份：恢复为新聊天｜查看内容｜下载文件
└─ 分割：指定范围｜固定楼层数｜增量分卷

原生聊天文件
└─ 当前聊天：备份｜分割
```
